# LongHorn v0.1 delivery plan

This records the agreed product direction: continue the existing modular
architecture until developers can run and use one complete LongHorn workflow.
Every implemented feature gets its own Markdown guide, connected through the
[feature index](features.md) and [architecture](architecture.md).

## 1. Account command history — implemented

Members can browse earlier commands and delivery status after restarting without
retaining every command ID. Pages are bounded, owner-scoped and cursor-based;
operators have an explicit deployment-wide view. Existing commands survive schema
upgrade, and unavailable/pruned delivery metadata stays distinguishable from success.
[Native evidence](command-history-testing.md) covers permissions, upgrade,
concurrent writes and restart. [History API](account-command-history.md) records
the live-pagination and unavailable-metadata boundaries.

## 2. Web console — implemented

A working browser flow connects signup/sign-in, command creation/history,
command/receipt detail and operator inspection, retry and audit history. Screens
use the real APIs and account policy, with useful loading, empty and failure states.
Verify accessibility and real screenshots before reporting screens complete.
[Console guide](web-console.md), [security](console-security.md),
[recovery](console-recovery.md) and [native verification](console-testing.md)
record the implemented flow and the real-device accessibility boundary.

## 3. One complete example application — implemented

Package the existing command/receipt workflow as a coherent example that developers
can run, inspect and adapt. Explain how account policy, DI, transactions,
idempotency, delivery and audit connect. The example must work through its actual
user flow, including receiver outage and recovery, rather than rely on fixtures
or seeded response data.
The [complete walkthrough](command-application.md) connects the working browser,
temporary native demo and persistent host. The browser/native gates verify actual
computed receipts, outage/recovery, ownership and attributed audits.

## 4. Setup and deployment — implemented

Provide a persistent starter/setup path with explicit runtime configuration,
schema deployment, operator provisioning, receiver storage and production ingress
settings. A new developer should be able to follow the documented steps without
reading this conversation. Keep owner/provisioning credentials separate from HTTP.
Verify the generated or packaged artifact independently of the workspace.
The [independent archive](command-app-distribution.md) contains editable source,
receiver, local framework snapshot, [runtime grants](runtime-role-grants.md) and
[deployment instructions](command-app-deployment.md). [Native verification](command-app-testing.md)
installs/builds it after relocation, deploys its actual schema/grants and uses its
browser/receiver workflow across outage and both processes restarting.

## 5. Release hardening — locally verified; hosted CI pending

Run permission and input-boundary checks, verify backup/restore of retained state,
add repeatable CI gates and document schema/configuration upgrades. Record the
supported runtime/deployment matrix and remaining limitations. A v0.1 release
requires evidence for the complete workflow and documentation, not only exported
package names or passing unit tests.
[Offline backup/restore](command-app-backup.md) proves retained state and a new
computed command in replacement database/storage. Runtime authority and input
denial are exercised by the native gate. [Upgrades](command-app-upgrades.md),
[support matrix](supported-runtimes.md) and [CI configuration](release-verification.md)
record the procedures and evidence. The connected private LongHorn repository was
found with its initial license; this implementation is being prepared on a review
branch. The hosted workflow has not run for this source, and no tagged/published release or cloud deployment
is claimed. That external verification remains before an actual v0.1 release.

Additional providers and transports remain later integrations in the
[roadmap](roadmap.md). This plan does not mark the overall product complete at
an intermediate feature milestone.
